# A4PRINT HUB — архитектура внутренней системы

## 1. Цель

Единая внутренняя система управления для двух направлений:

- А4-Принт
- 3D-ARTPRINT

Оба направления работают с общей базой клиентов, товаров, услуг, складских остатков, заказов, сотрудников и внутренних сообщений.

## 2. Основные модули

1. **Главная** — сводка по заказам, складам, задачам и уведомлениям.
2. **Заказы** — единый журнал заказов с источником и направлением бизнеса.
3. **Клиенты** — карточки клиентов и история заказов/обращений.
4. **Товары** — номенклатура, категории, цены, единицы измерения.
5. **Услуги** — услуги А4-Принт и 3D-ARTPRINT, тарифы и параметры.
6. **Склад** — остатки, приходы, расходы, перемещения, минимальные остатки.
7. **Производство** — задания, исполнители, сроки и статусы.
8. **Каталог 3D** — модели, URL исходной модели, параметры и связь с заказом.
9. **Сообщения** — общий чат, личные чаты и сообщения, привязанные к заказу/задаче.
10. **Уведомления** — новые заказы, низкие остатки, сообщения и изменения статусов.
11. **Отчёты** — продажи, расход материалов, остатки и загрузка производства.
12. **Сотрудники и права** — роли и разрешения.

## 3. Направления бизнеса

Каждый заказ и движение склада имеют `business_unit`:

- `A4_PRINT`
- `3D_ARTPRINT`
- `COMMON`

Это позволяет вести общий склад и одновременно строить отчёты отдельно по каждому направлению.

```text
   └── ORDERS

         ├── PRODUCTION_JOB
         └── MESSAGES
```

## 6. Заказ с сайта 3D-ARTPRINT

Текущий сайт должен передавать в API единый объект заказа:

```json
{
  "business_unit": "3D_ARTPRINT",
  "customer": {
    "name": "...",
    "phone": "...",
    "email": "..."
  },
  "model": {
    "name": "...",
    "source_url": "..."
  },
  "print": {
    "method": "...",
    "material": "...",
    "color": "...",
    "dimensions": "...",
    "infill": "...",
    "quantity": 1
  },
  "price": 0,
  "comment": "..."
}
```

После сохранения API возвращает номер заказа. Email остаётся дополнительным уведомлением, а не единственным хранилищем.


```text

```


## 9. Склад

Остаток не редактируется вручную как единственный источник истины. Он рассчитывается из движений или поддерживается транзакционно:

```text
RECEIPT      +
ISSUE        -
TRANSFER     +/-
ADJUSTMENT   +/-
RETURN       +
```

Каждое движение содержит пользователя, дату, склад, товар, количество, причину и связанный документ/заказ.

## 10. Безопасность

GitHub используется для кода, но **не для хранения клиентских данных и секретов**.

База должна быть отдельным защищённым сервисом с авторизацией и разграничением доступа. Секретные ключи API не помещаются в публичный frontend.

## 11. Этапы разработки

### Этап 1 — фундамент

- база данных;
- авторизация;
- сотрудники и роли;
- направления бизнеса;
- товары и услуги;
- склады и остатки.

### Этап 2 — заказы

- единый журнал;
- карточка заказа;
- статусы;
- история изменений;
- интеграция 3D-ARTPRINT;
- Email-уведомления.

### Этап 3 — производство

- задания;
- исполнители;
- сроки;
- расход материалов;
- связь заказа со складом.

### Этап 4 — коммуникации

- общий чат;
- личные сообщения;
- сообщения внутри заказа;
- уведомления.

### Этап 5 — аналитика

- выручка;
- заказы по направлениям;
- расход материалов;
- складские остатки;
- популярные услуги/модели;
- производственная загрузка.

## 12. Принцип

**Один клиент → одна история.**

**Один товар → один общий остаток.**

**Один заказ → единая карточка со всеми действиями и сообщениями.**

**А4-Принт и 3D-ARTPRINT → разные направления одной системы.**
